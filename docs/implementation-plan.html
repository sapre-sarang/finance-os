Build the picture from statements you already have

Version one reads CSV, OFX, QIF and text-based PDF statements, lets you review them, and turns them into accounts, budgets and net worth. No bank logins, no paid APIs.

Draft plan, written against docs/product-spec.md. This plan settles spec open decision 1: text-based PDF import is in v1. Scanned-document OCR is not.

Try the de-duplication rule

Each transaction gets a key: account, date, amount and cleaned-up description. For each key, v1 adds only the rows the database does not already hold.

Import flow

Nothing is saved until you have looked at it. The first pass is a preview that writes nothing; the second is a commit you confirm.

  1. UploadSign-in check, size limit, file type by contentapps/api
  2. ParseCSV, OFX, QIF or PDF text into one normalized shapepackages/core
  3. ValidateStrict schema on every parsed row, injection-safe textpackages/core
  4. De-duplicateCount rule above, possible duplicates flaggedpackages/core
  5. ReviewFix categories, skip rows, resolve flagsapps/web
  6. CommitAll rows or none, batch recorded with a file hashapps/api

Parsers are plain Python that take bytes and return rows. They import neither FastAPI nor the database, so every parser is tested with synthetic files alone.

Libraries, all free and local

  • CSV with the standard library; QIF with a small hand-written parser; OFX with ofxtools or ofxparse.
  • PDF text and tables with pdfplumber. One bank layout first; a second parser only when a second real layout exists.
  • Password-protected PDFs are opened in memory with a password you type. It is never stored.
  • Each library is checked for maintenance and known vulnerabilities before it is added.

Milestones

  1. M0

    Scaffold

    Needs your go-ahead before any dependency is installed

    • packages/core with pytest, strict mypy and ruff; apps/api with FastAPI.
    • packages/db, apps/web (Vite, strict TypeScript, Tailwind, Vitest), Postgres through Docker Compose.
    • CI workflow, and CLAUDE.md and READMEs updated with the real commands.
  2. M1

    Core primitives

    • Money as integer minor units plus an ISO currency code. Amounts parse from decimal strings, never floats.
    • UTC timestamps, with the date a transaction occurred kept apart from when it was imported.
  3. M2

    Persistence and sign-in

    • SQLAlchemy models and Alembic migrations.
    • One local user, Argon2 password hash, server-side session in an HttpOnly cookie. Every route checks the session; none trusts a user ID from the client.
    • Account identifiers encrypted at rest, key from an environment variable.
    • Accounts and transactions create, read, update and delete, validated with Pydantic.
  4. M3

    Import pipeline

    The heart of v1

    • Parsers in order: CSV, OFX, QIF, then the first text-PDF layout.
    • Limits on upload size and row count, content-based type check, and neutralized leading = + - @ in text fields.
    • Occurrence-count de-duplication as shown above. When the format supplies the bank's own transaction ID (OFX FITID), that ID is the key.
    • Possible duplicates appear in the review step. They are never dropped silently.
    • Import batches store the file hash only. The raw file is not kept by default.
  5. M4

    Categories, recurring items, holdings

    • Rule engine with explicit priority, so the same transaction always gets the same category. A manual category always wins.
    • Subscriptions, EMIs and SIPs as manual records. History can suggest a recurring item; it never creates one on its own.
    • Equity, mutual fund and fixed-deposit holdings with valuation history in minor units.
  6. M5

    Net worth and budgets

    • Net worth at any date is account balances plus holdings, minus liabilities such as cards and loans.
    • Monthly budgets against actuals and category breakdowns. A transaction is counted once, and transfers between your own accounts are excluded.
    • Currency is stored on every amount. One display currency, no conversion in v1.
  7. M6

    Web app

    • Sign-in, accounts, transactions, the import wizard (upload, preview, resolve, commit), rules, recurring items, holdings, net-worth chart, budgets and reports.
    • Zod validation on forms, TanStack Query for data.
  8. M7

    Hardening

    • Playwright end-to-end run from import to report.
    • pnpm audit and a Python vulnerability scan in CI.
    • Threat-model note in docs/, and a final check that no real data or secrets are in the repository.

Testing

Every fixture is synthetic: invented names, round amounts, fictional account numbers. Sample PDFs are generated by code so no real statement ever enters the repository.

AreaWhat gets tested
Money and datesArithmetic in minor units, rounding, UTC handling, occurred date versus import date
ParsersGolden files per format; malformed, oversized and wrong-type files rejected with no partial rows
De-duplicationSame file twice, overlapping statements, genuine repeat purchases stay separate
CategorizationSame input and rules give the same category; priority order; manual override
Net worth and budgetsAssets minus liabilities at a date, each transaction counted once, own-account transfers excluded
APIEach endpoint has a happy path and a validation failure; unauthenticated requests are refused

Decisions needed

Which bank's PDF layout comes first?
A synthetic sample that mimics its layout is enough. Please do not commit a real statement.
Should uploaded files be kept?
Recommended: no. Keep the file hash and parsed rows only. That removes the stored-statement risk entirely.
How does sign-in work?
Recommended: one local user created by a setup command, with a password and session cookie.
Which display currency?
Proposed: INR, changeable in config.yml.
Where do we start?
Recommended: scaffold core and api only, build M1 to M3, and add the web app once imports work end to end.
FinanceOS is pre-MVP. This page contains no real financial data.
